We are building **FlashCart**, a high-concurrency e-commerce flash sale platform that allows customers to purchase limited-stock products during time-sensitive promotional events.

The platform must handle sudden traffic spikes, prevent overselling, process orders reliably, and provide customers with a fast and consistent checkout experience.

# Part 2 — A Day in the Life

I work as a backend software engineer on the FlashCart team. My main responsibilities include inventory reservation, order creation, and high-concurrency flash sale workflows.

My day starts with our Daily Standup at 9:15 a.m. Hannah, our Scrum Master, opens the Jira board and facilitates the meeting.

Each team member briefly explains what they completed yesterday, what they plan to work on today, and whether they have any blockers.

When it is my turn, I explain that I completed the first version of the inventory reservation API. Today, I plan to add Redis-based atomic inventory deduction and integration tests.

I also mention a business ambiguity. I do not know how long we should reserve inventory for a customer who creates an order but does not complete payment.

Because this is a business requirement question, Hannah asks me to speak with Priya after the standup. We do not spend fifteen minutes discussing it during the standup because the issue only affects a few people.

After the meeting, I send Priya a message in Slack. She confirms that inventory should be reserved for fifteen minutes. If payment is not completed within that time, the order should be cancelled and the inventory should be released.

I add the decision to the Jira ticket so that QA, frontend engineers, and other backend engineers can see the same requirement. Important decisions should not remain only in private Slack messages.

I update my local main branch and create a new feature branch. I never make changes directly on the main branch.

I implement the inventory reservation logic using Java, Spring Boot, Redis, and a Lua script. The Lua script checks the remaining stock, verifies that the customer has not already purchased the product, deducts the inventory, and creates a reservation event atomically.

Around 11:00 a.m., I review the API contract with Sophia, one of our frontend engineers. She needs clear responses for successful reservations, sold-out products, duplicate purchase attempts, and rate-limited requests.

We agree on the response codes and payload format. I update the OpenAPI documentation and add the decision to the Jira ticket.

Before lunch, I complete the initial implementation and write unit tests and integration tests. I review my own code changes line by line before committing them.

I push the feature branch and create a pull request in GitHub. I link the pull request to the Jira ticket and request reviews from Ethan and Victor.

After lunch, I attend Backlog Refinement. Priya introduces a new business requirement: customers should be able to join a virtual waiting room before a large flash sale begins.

Emily presents the proposed user flow in Figma. The frontend engineers ask how the customer’s queue position should be displayed. The backend engineers discuss token generation, rate limiting, Redis expiration, and fairness.

Victor explains that this feature affects several services and requires a technical design document. We split the feature into smaller Jira stories for the waiting-room UI, queue-token service, rate limiter, monitoring dashboard, and load testing.

One ticket is estimated at thirteen story points. The team agrees that it is too large and uncertain, so we divide it into smaller tickets.

Later, Ethan leaves comments on my pull request. He notices that one retry could create duplicate reservation events. Victor also recommends adding an idempotency key to the API.

I update the implementation and add tests for duplicate requests and Redis timeouts. After the changes are approved, I merge the pull request into the development branch.

The GitHub webhook triggers our Jenkins pipeline. Jenkins checks out the code, runs unit and integration tests, builds a Docker image, pushes the image to Amazon ECR, and deploys it to our development environment on Amazon EKS.

The pipeline succeeds, and Olivia begins testing the feature in the QA environment.

During a concurrent load test, Olivia discovers that the API occasionally creates more reservations than the available stock. She creates a critical Jira bug with the test configuration, logs, timestamps, expected result, and actual result.

I reproduce the issue and discover that one fallback code path updates the database directly instead of using the Redis Lua script. That path is not atomic and allows a race condition.

I immediately notify Victor, Olivia, Priya, and Hannah. Because overselling is a critical business issue, we stop the planned release.

I fix the fallback logic, add a concurrency test, and create another pull request. After code review, CI/CD deployment, and another load test, the total number of successful reservations matches the available inventory exactly.

Olivia verifies the fix and closes the bug. Priya confirms that the release can continue.

At the end of the day, I update my Jira tickets and post a short summary in Slack. I explain what was completed, what still needs testing, and whether there are any remaining release risks.

## How Your Team Works

### 9. How long are your sprints and why?

Our Sprints are two weeks long.

Two weeks gives us enough time to build, test, and demonstrate a meaningful feature while still receiving feedback quickly.

A one-week Sprint would create too much ceremony and release overhead. A one-month Sprint would delay feedback and increase the risk of building the wrong solution.

### 10. What happens during Sprint Planning?

During Sprint Planning, Priya presents the highest-priority Product Backlog items and explains the business value and acceptance criteria.

The team asks questions, identifies dependencies, and discusses the technical implementation. We split large stories into smaller tasks and estimate them using Fibonacci story points.

Story points represent relative effort, complexity, and uncertainty. They do not directly equal a fixed number of hours.

We then consider our previous velocity, team capacity, vacations, production support, and current risks. Finally, we select a realistic Sprint Backlog and agree on a Sprint Goal.

### 11. What does your Daily Standup look like?

Our Daily Standup starts at 9:15 a.m. and normally lasts fifteen minutes. Hannah facilitates it.

Each person explains what they completed yesterday, what they plan to do today, and whether they have any blockers.

We do not solve detailed technical problems during the standup. The relevant people stay after the meeting or create a separate discussion.

### 12. What is a Sprint Review and who attends?

A Sprint Review is where we demonstrate completed working software and collect feedback.

Our entire Scrum team attends, including the Product Owner, Scrum Master, engineers, QA, DevOps, database engineer, and designer.

We may also invite marketing teams, customer-support teams, sellers, or other stakeholders. For example, we may demonstrate a new promotion dashboard or waiting-room experience.

Priya collects the feedback and adds appropriate follow-up items to the Product Backlog.

### 13. What is a Retrospective and what does your team do in it?

A Retrospective is where we discuss how the team worked during the Sprint.

We usually discuss what went well, what did not go well, and what we should improve. We focus on processes and systems instead of blaming individuals.

For example, after an overselling bug, we might discuss why our tests did not cover one fallback path, why the code review missed it, and how we can improve our concurrency testing.

At the end, we select one or two specific improvement actions and assign an owner.

### 14. What is Backlog Refinement and when do you do it?

Backlog Refinement is when we prepare future Product Backlog items before Sprint Planning.

We do it once a week. Priya explains upcoming requirements, Emily presents designs, and the engineering team discusses dependencies, risks, and technical options.

We clarify acceptance criteria, split large stories, and provide preliminary estimates. Our goal is to make sure the highest-priority tickets are ready before Sprint Planning.

### 15. What is your team’s Definition of Done?

A ticket is done when all acceptance criteria are satisfied and the implementation has been reviewed and approved.

Unit tests, integration tests, and any required concurrency or performance tests must pass. The Jenkins pipeline must be green, and the feature must be deployed to the QA or staging environment.

Olivia must verify the behavior, and there cannot be any unresolved critical or high-severity bugs. Required documentation, monitoring, database migrations, and configuration changes must also be completed.

## Communication and Escalation

### 16. You found a critical bug two days before release. What do you do?

I would not wait until the next Daily Standup.

I would immediately create a critical Jira bug and notify Olivia, Victor, Hannah, Priya, and Noah in our release or incident Slack channel.

I would include the business impact, affected environment, reproduction steps, logs, and any known workaround.

The team would pause the release and perform a quick triage. We would decide whether to fix the problem, disable the feature, roll back the change, or remove it from the release.

The fix would still require code review, automated tests, regression testing, and release approval.

### 17. A stakeholder wants to add a feature mid-sprint. What happens?

I would send the request to Priya, our Product Owner.

Normally, we would not add a new feature directly to an active Sprint because that would interrupt the Sprint Goal.

Priya would evaluate its urgency and business value with Hannah and Victor. If it is not urgent, she would add it to the Product Backlog.

If it is an emergency, such as a security, compliance, or major revenue issue, we may bring it into the Sprint. However, we would normally remove another item of similar size and communicate the change to the whole team.

### 18. You are blocked and cannot finish before the sprint ends. Who do you talk to?

I raise the blocker as soon as I recognize it.

For a technical problem, I talk to Victor or another experienced engineer. For a business requirement question, I talk to Priya. For a database issue, I work with Daniel. For an environment or access problem, I contact Noah.

I also notify Hannah so she can track the blocker and coordinate with other teams if necessary.

If we still cannot finish, we explain the situation, separate any completed work when possible, and return the unfinished portion to the Product Backlog.

### 19. Two engineers disagree on a technical approach. How is it resolved?

First, both engineers explain their approach using the same evaluation criteria, such as scalability, consistency, performance, maintainability, complexity, cost, and delivery risk.

For example, they may compare database locking with Redis-based inventory reservation.

If necessary, we create a small proof of concept or write an Architecture Decision Record.

We try to reach agreement as a team. If we still cannot agree, Victor makes the final technical decision and documents the reasoning.

### 20. The designer is out sick and you need assets. What do you do?

We first check whether the feature can use an existing component from our design system.

If it follows an approved pattern, the frontend engineers can continue and document their assumptions.

We do not invent a major new customer experience without Emily. We can continue with backend APIs, data contracts, automated tests, or nonvisual frontend work.

Hannah may also help us move another ready ticket forward so the team is not completely blocked.

### 21. The deployment pipeline breaks and blocks the team. Who owns it?

Noah is the primary owner because he maintains the pipeline, but the entire team helps resolve the problem.

Developers provide the failing commit, logs, and recent application changes. Daniel helps if a database migration caused the failure, and Victor helps if the problem involves architecture or service configuration.

We may temporarily pause merges until the pipeline is restored. Afterward, we add tests, alerts, or documentation to prevent the same failure from happening again.

## Documentation and Artifacts

### 22. What is a Product Backlog and who owns it?

The Product Backlog is the prioritized list of all potential product work.

It includes new features, bugs, technical debt, infrastructure work, security improvements, performance improvements, and research tasks.

Priya owns and prioritizes the Product Backlog. However, everyone can contribute items.

For example, I may add a performance improvement, Olivia may add a testing task, Noah may add an infrastructure task, and Daniel may add database optimization work.

### 23. What is a Sprint Backlog and how is it created?

The Sprint Backlog contains the Product Backlog items selected for the current Sprint, along with the technical tasks needed to complete them.

It is created during Sprint Planning.

Priya explains the priorities, and the engineers decide how much work the team can realistically complete. We split the stories into smaller tasks and create a Sprint Goal.

Once the Sprint begins, the development team owns the Sprint Backlog.

### 24. When do you write a technical design document?

We write a technical design document when a feature affects multiple services, changes a major API contract, introduces a new database model, or has important scalability, security, or consistency requirements.

For example, a virtual waiting room, inventory reservation system, or delayed order-cancellation workflow would require a design document.

The engineer leading the feature writes the first draft. Victor approves the architecture. Daniel reviews database sections, Noah reviews infrastructure sections, and Olivia reviews the testing strategy.

Affected engineers also review the document before implementation begins.

### 25. How does your team file and track bugs?

We create bugs in Jira using a standard template.

The ticket includes the environment, severity, expected result, actual result, reproduction steps, logs, screenshots, videos, and affected users.

We classify bugs from P0 to P3. A bug that causes overselling, incorrect payment, or platform unavailability would normally be P0 or P1.

The fix pull request is linked to the Jira ticket. Olivia verifies the fix in the correct environment before closing the bug.

### 26. Where does your team write things down?

We use Jira for stories, tasks, bugs, acceptance criteria, ownership, and status.

We use Confluence for product requirements, technical designs, runbooks, and Architecture Decision Records.

We use Slack for fast communication, but important decisions are copied into Jira or Confluence.

We use GitHub for code, pull requests, and review history. Emily uses Figma for UI designs. Jenkins manages CI/CD. Grafana, Prometheus, and AWS CloudWatch are used for logs, metrics, dashboards, and alerts.

## Bigger Picture

### 27. How does your team decide what goes into the next sprint?

Priya prioritizes Product Backlog items based on customer value, revenue impact, urgency, risk, and stakeholder needs.

During Backlog Refinement, the team adds technical information, dependencies, acceptance criteria, and estimates.

During Sprint Planning, we compare those priorities with our capacity and previous velocity. We also reserve some capacity for bugs, production support, and operational work.

We then select a realistic amount of work and define a Sprint Goal.

### 28. What happens if your team consistently does not finish sprint work?

We treat it as a process problem rather than blaming individual engineers.

During the Retrospective, we check whether we are overcommitting, estimating poorly, accepting unclear requirements, ignoring dependencies, or receiving too many production interruptions.

We may reduce our Sprint commitment, improve refinement, split stories into smaller tickets, or reserve more capacity for operational work.

Future planning should use our actual velocity rather than an unrealistic target.

### 29. How does a brand-new feature go from idea to production?

A new feature normally begins with a business or customer problem.

Priya validates the problem and defines the business goal. Emily may create a user flow and Figma design.

The team refines the feature, defines acceptance criteria, identifies dependencies, and writes a technical design document when necessary.

During Sprint Planning, we select the ready stories. Developers work on feature branches, write tests, create pull requests, and receive code reviews.

Jenkins runs automated tests, builds Docker images, pushes them to Amazon ECR, and deploys them to Amazon EKS.

Olivia tests the feature, Priya verifies the business behavior, and Noah manages the production release. After release, we monitor logs, metrics, error rates, latency, and business results.
