## 1. Point-to-point vs publish-subscribe model, pros and cons for each

**中文：**
 Point-to-point 是一个 message 只会被一个 consumer 消费，常见例子是 queue。
 它的优点是简单、适合任务分发，比如订单处理或异步 job。
 缺点是如果多个系统都需要同一份消息，就不太方便，因为消息被一个 consumer 拿走后就没了。
 Publish-subscribe 是一个 message 可以被多个 subscribers 消费，适合事件广播，但系统复杂度会更高。

**English:**
 Point-to-point means one message is consumed by one consumer, usually through a queue.
 The benefit is that it is simple and good for task distribution, like order processing or async jobs.
 The downside is that it is not ideal when multiple systems need the same message.
 Publish-subscribe means one message can be delivered to multiple subscribers, so it is good for event broadcasting, but it adds more system complexity.

## 2. Why message system?

**中文：**
 Message system 主要用来做异步通信，让 producer 和 consumer 解耦。
 它可以削峰填谷，避免高峰流量直接打到下游服务。
 它也可以提高系统可靠性，因为消息可以暂存在 broker 里，consumer 慢一点也不会马上丢数据。
 在分布式系统里，它常用于 event-driven architecture，比如订单创建后通知支付、库存、邮件服务。

**English:**
 A message system is mainly used for async communication and decoupling producers from consumers.
 It helps absorb traffic spikes, so downstream services do not get overwhelmed directly.
 It also improves reliability because messages can stay in the broker while consumers catch up.
 In distributed systems, it is often used for event-driven architecture, like sending order events to payment, inventory, and email services.

## 3. Kafka architecture

**中文：**
 Kafka 主要由 producer、broker、topic、partition、consumer 和 consumer group 组成。
 Producer 把消息写到 topic，topic 会被切成多个 partition 来提高并发和吞吐量。
 Broker 负责存储数据，partition 通常会有 replicas 来提高容错能力。
 Consumer group 里的多个 consumer 可以并行消费不同 partitions，同一个 partition 在一个 group 里同一时间只能被一个 consumer 消费。

**English:**
 Kafka mainly has producers, brokers, topics, partitions, consumers, and consumer groups.
 Producers write messages to topics, and topics are split into partitions for higher parallelism and throughput.
 Brokers store the data, and partitions usually have replicas for fault tolerance.
 Consumers in the same consumer group can consume partitions in parallel, but one partition can only be consumed by one consumer in that group at a time.

## 4. Message accumulated in Kafka, consumer can't consume all the data on time, what should you do?

**中文：**
 首先我会看 consumer lag，确认是消费速度慢、下游慢，还是 consumer 出错。
 如果是消费能力不够，可以增加 consumer instances，但前提是 topic 有足够的 partitions。
 如果是单条消息处理太慢，可以优化业务逻辑、批量处理、异步写下游，或者扩容下游服务。
 如果只是短期流量高峰，Kafka 可以暂存消息，但要确保 retention 时间和磁盘容量足够。

**English:**
 First, I would check consumer lag to understand whether the consumer is slow, the downstream service is slow, or the consumer has errors.
 If the consumer capacity is not enough, I can add more consumer instances, but the topic needs enough partitions.
 If each message takes too long to process, I would optimize the logic, use batch processing, write downstream asynchronously, or scale the downstream service.
 If it is only a short traffic spike, Kafka can buffer the messages, but I need to make sure retention and disk space are enough.

## 5. How does Kafka deal with the expired data?

**中文：**
 Kafka 不会像普通 queue 一样消费完就马上删除消息。
 它主要通过 retention policy 删除过期数据，比如按时间 retention.ms 或按大小 retention.bytes。
 当消息超过保留时间，或者 partition log 超过限制，Kafka 会删除旧的 log segment。
 所以 Kafka 的数据生命周期主要由 topic-level 或 broker-level 的 retention 配置控制。

**English:**
 Kafka does not delete a message immediately after it is consumed like a normal queue.
 It removes old data based on retention policy, such as retention.ms or retention.bytes.
 When messages are older than the retention time, or the partition log is too large, Kafka deletes old log segments.
 So the data lifecycle in Kafka is mainly controlled by topic-level or broker-level retention settings.

## 6. Data volume in Kafka?

**中文：**
 Kafka 很适合处理大数据量和高吞吐场景，因为它是顺序写磁盘，性能很高。
 数据量主要受 broker 数量、磁盘容量、partition 数量、副本数和 retention 配置影响。
 实际设计时，我会估算 daily traffic，比如每秒多少条消息、每条消息多大、保留几天、replication factor 是多少。
 公式大概是：daily data = QPS × message size × 86400 × replication factor，然后再乘以保留天数。

**English:**
 Kafka is good for large data volume and high throughput because it writes data to disk sequentially.
 The data volume depends on the number of brokers, disk size, partitions, replication factor, and retention settings.
 In real design, I would estimate daily traffic, like messages per second, message size, retention days, and replication factor.
 A rough formula is: daily data = QPS times message size times 86400 times replication factor, then multiply by retention days.

## 7. How to calculate partition number?

**中文：**
 Partition 数量主要取决于吞吐量、consumer 并发度和未来扩展需求。
 一个 consumer group 里，最大并行消费数通常不会超过 partition 数量。
 所以如果我需要 10 个 consumer 并行消费，topic 至少要有 10 个 partitions。
 实际还要看单个 partition 的吞吐能力、broker 数量、key-based ordering 需求，以及不要创建过多 partitions 增加管理成本。

**English:**
 The number of partitions depends on throughput, consumer parallelism, and future scaling needs.
 In one consumer group, the max parallelism is usually limited by the number of partitions.
 So if I need 10 consumers to consume in parallel, the topic should have at least 10 partitions.
 In practice, I also consider single-partition throughput, broker count, key-based ordering, and the overhead of having too many partitions.

## 8. AWS SQS vs RabbitMQ vs Kafka

**中文：**
 SQS 是 AWS managed queue，适合简单异步任务，不需要自己维护 broker。
 RabbitMQ 是传统 message broker，支持复杂 routing，比如 exchange、routing key、work queue。
 Kafka 更像 distributed event log，适合高吞吐、事件流、日志收集和数据 pipeline。
 简单说，SQS 适合托管队列，RabbitMQ 适合灵活 routing，Kafka 适合大规模 event streaming。

**English:**
 SQS is an AWS managed queue, good for simple async tasks without managing brokers yourself.
 RabbitMQ is a traditional message broker and supports flexible routing, like exchanges, routing keys, and work queues.
 Kafka is more like a distributed event log, good for high throughput, event streaming, log collection, and data pipelines.
 So simply speaking, SQS is good for managed queues, RabbitMQ is good for flexible routing, and Kafka is good for large-scale event streaming.

## 9. AWS SNS vs SQS

**中文：**
 SNS 是 publish-subscribe 服务，主要用来把一个 message fan out 给多个 subscribers。
 SQS 是 queue 服务，主要用来让 consumer 异步拉取并处理消息。
 SNS 通常是 push model，SQS 通常是 pull model。
 实际系统里经常把 SNS 和 SQS 一起用：SNS 负责广播事件，多个 SQS queue 分别给不同服务消费。

**English:**
 SNS is a publish-subscribe service, mainly used to fan out one message to multiple subscribers.
 SQS is a queue service, mainly used for consumers to pull and process messages asynchronously.
 SNS is usually a push model, while SQS is usually a pull model.
 In real systems, SNS and SQS are often used together: SNS broadcasts the event, and different SQS queues let different services consume it.
